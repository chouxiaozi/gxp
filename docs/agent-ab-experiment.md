# agent A/B 实验 — gxp vs rg+jq+ast-grep（2026-11-09）

> **目的**：验证 gxp 核心主张"一门 DSL < rg+jq+ast-grep 多工具往返成本"（AGENTS.md §0.1 场景驱动判据要求的证据，此前为零）。结论决定 v1.0 方向：显著优势 → 发布准备；无优势 → 定位重议；混合 → 按场景收敛 v1 范围。

## 1. 方法学

- **被试**：同一模型的独立子 agent ×16（§0.2 场景 A-H 各 1 任务 × 2 臂），零上下文启动（不知道答案）。
- **G 臂**：只允许 `gxp`（v0.47.0，含 l3-structural）；禁用 rg/grep/jq/ast-grep 及内置 Grep/Read 工具。
- **R 臂**：只允许 `rg`（15.2.0）+ `jq`（1.8.2）+ `ast-grep`（0.51.1，仅 C 任务需要）；禁用 gxp/GNU grep 及内置工具。
- **测量指标**：① 命令行工具调用次数（agent 自报 + 诚实指令）；② 答案正确性（对照 §3 基准答案，运行前冻结）；③ 摩擦记录（定性）。**wall-clock 不作指标**（16 agent 并行调度干扰）。token 消耗以"调用次数 × 输出体积"近似（局限性如实声明）。
- **公平性**：两臂任务文本完全相同；同一台机器同一时段；均为当日新装/新编译工具（Defender spawn 税等同）。

### 3.1 GT 计算过程的方法学发现（重要，防复发）

1. **GNU grep 3.0（Windows 移植版）ERE `{n}` 区间表达式损坏**：`[0-9]{2}Z` 计数 11,859 vs 显式 `[0-9][0-9]Z` 118,590，**恰好 10×**。GT 正则一律用显式字符类；本发现亦影响"BARE ≡ grep -E 对账"的测试方法选择（tests 的 ERE 对账若用区间表达式，在 Windows GNU grep 3.0 上不可靠——当前测试未用区间，无影响，但新增对账测试时禁止区间）。
2. **语料含非法时间戳（设计意外变特性）**：生成器 PowerShell `[int]` 是**四舍五入**而非截断，产生 hour=24（120,600 行）与 minute=60（54,270 行）非法时间戳。gxp speedate 正确拒绝（不参与 _ts 谓词）；文本工具（rg/grep 子串）会误纳。D 任务因此天然考察**语义正确性**差异：文本近似会得出 120,734（多 2,010 条 T12:60:xx 无效行），正确答案 118,724。
3. **gxp capture 正则内嵌 `"` 返回 0 行**（`/"trace_id":"..."/` 语法；无引号版本正常）——解析限制，两臂 agent 如实遇到如实记录，不计入公平性调整。
4. 差异排查纪律：本实验 GT 冻结阶段曾把 gxp D2 答案误读为 23,724（实际输出 23,718），引发一轮 count-stage bug 误报——三口径复核（count stage = --json 原始行数 = 文本行数 = 23,718）+ 50MB 切片 `--verify` PASS 后澄清。**教训：交叉验证不一致时，先复核自己的转述，再怀疑工具。**

**指标结论**：
- **正确率**：16/16 vs 16/16，平——该任务难度下两臂（强模型、零上下文）都能收敛到正确答案
- **调用轮次**：R 臂少 22%（3.125 vs 4.0）
- **token 消耗**：G 臂少 9%（31,140 vs 34,252；jq 编程 token 重，F-R 手写采样 47.8k 全场最高）
- **有效查询轮次**（剔除 help/语法试错/限流吞调用/verify/交叉验证后分解）：G ≈13 vs R ≈13，**打平**——G 臂多出的 7 轮全部是：发现成本（--help×2、字符串等值语法试错×2、限流吞×3）+ 自发 `--verify`×2；R 臂对应开销：rg×jq 双引擎交叉验证×7 + 限流×1
- **时长参考**（污染严重仅供参考）：G 臂合计 1,424s vs R 臂 1,944s（−27%，含限流等待）

**结构性不对称（轮次差距的根因）**：
1. **发现成本不对称**：rg/jq 在模型预训练分布内（零发现成本）；gxp 是新 DSL，每个 agent 冷启动都要付 `--help` + 语法试错——这是真实世界效应，但随会话摊薄
2. **融合能力不对称**：shell 管道允许 R 臂把 `rg | jq` 压进单轮调用；gxp 动词组合发生在进程内，agent 无法跨进程融合

**场景级质性发现**（信息量最大的部分）：
- **F（抽样）是 gxp 价值最鲜明例证**：内建 `| sample 20`（3 轮）vs R 臂在 jq 内手写 Park–Miller LCG + 蓄水池采样 Algorithm R（5 轮、47.8k tokens）——语义缺口靠生成式编程填补，实现负担转移给了模型
- **G（去重）是 gxp 最难堪场景**：capture 正则 `trace_[0-9]+` 被任务描述暗示误导（只捕 18,700 十进制值），9 轮才修正为 hex；R 臂 jq 结构化字段访问 `.trace_id` 2 轮直取，根本不经过格式歧义——**正则捕获 vs 结构化字段访问的语义鸿沟**。注：gxp 其实有 `distinct by trace_id` 字段路径（无需 capture），但 G 臂 agent 被提示示例锚定未尝试（提示偏置，见局限 2）
- **C（AST）**：ast-grep+jq 单管道 1 轮 < gxp 分步 4 轮——gxp 的 count/group/--verify 分步反而多花轮次
- **--verify 是 gxp 独有置信资产**：D-R agent 自述"rg 无 JSON 语义，单靠正则不可信"被迫双引擎对账；G 臂 agent 用一次 `--verify` 达成同等置信
- **jq 全量解析 900MB 近分钟级**（B-R 报告）且 PowerShell 管道中转大数据流拖慢（G-R/H-R 报告）——R 臂的轮次优势有运行时代价

**局限（如实声明）**：
1. n=1/格——单 agent 策略选择可摆动均值（G 场景 9 vs 2 轮即例证），无方差估计
2. 提示示例偏置：G 臂提示含 gxp 用法示例（G 任务的示例恰好是 capture 语法，锚定了 agent 路径），R 臂无示例——不完全对称
3. 限流噪声：≥5 个 agent 各报 1 次调用被吞（两臂等同存在）
4. 调用数为 agent 自报（诚实指令约束，未独立核验）
5. wall-clock 不作指标（16 并行调度干扰）；时长仅参考
6. 单模型、单日、单机、强模型——见 §5 弱模型假设

## 5. 结论：**混合 → 按场景收敛 v1 范围**（三选一之第三）

- 主张"一门 DSL < 多工具往返成本"：**轮次维度不成立**（4.0 vs 3.125，有效轮次打平）；**token 维度部分成立**（−9%）；**认知负担维度方向性成立但本实验无法定论**——R 臂的英雄式 workaround（手写蓄水池采样、多层区间正则、jq reduce 去重）说明语义缺口被"生成式编程"填补了。强模型填得动（16/16 全对）；**弱模型是否填得动是 gxp 价值主张的真正试金石，留作后续实验**
- gxp 优势集中区：**语义谓词场景**（F 抽样 / B 数值 / D 时间——R 臂在这三个场景轮次全输或付出最高 token）+ **--verify 置信资产** + 输出 token 更省
- rg+jq 优势区：纯文本/结构化字段场景（C/E/G），shell 管道融合 + 预训练熟悉度
- **v1.0 前行动建议**（按实证强度排序，接 Rust 方案 §11.3）：
  1. **字符串等值谓词**（如 `level="ERROR"`）：3/8 个 G 臂 agent 撞上的最大摩擦源（全部自发 workaround 到 `in [...]`）。升级条件已满足（§0.1 第 1 条场景驱动：A/D/F 三场景实证）。注意 D5 数值契约不动——等值仅对字符串字段生效
  2. **--help 强化**：字段谓词写法示例、`group by` 输出说明、line_no 基数——发现成本的主要来源
  3. **group by 结果排序**（或允许 rank 组合；涉及 B1 终止 stage 语义取舍，需设计评审）
  4. **字段路径一等公民宣传**：G 场景教训——`distinct by FIELD` 已支持但 agent 不知道；文档/help 中把"字段直取优先于 capture 正则"写进示例
- 后续实验方向：① 弱模型复跑 F/G 场景（检验"实现负担转移"假设）；② n=3 方差估计；③ 会话内摊薄实验（同 agent 连续 10 任务，观察 gxp 发现成本摊薄后轮次是否反超）
